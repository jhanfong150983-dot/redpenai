# 題型一致性 · 落地計畫

> 2026-09-07 · 配套文件：`題型分類權威表_2026-09-07.md`（31 型定義／步驟 2 框／步驟 3 批改鏈／尚缺清單）

**原則**：每階段都配「**檢測方法**（怎麼量）＋**確認方式**（過關門檻）」；關鍵階段把事件寫進 Supabase log 表做**線上監控**。依存嚴格：Phase 1 是地基，後面才動。全部改動 forward-only（不重跑舊卷），每階段留 kill-switch。

## 貫穿機制：Supabase 監控 log 表 `qtype_pipeline_log`

一條 log 流覆蓋整個一致性故事（分類→擷取→老師改→批改）。DDL（**待核准後手動跑**）：

```sql
create table if not exists qtype_pipeline_log (
  id            uuid primary key default gen_random_uuid(),
  created_at    timestamptz not null default now(),
  stage         text not null,        -- 'classify' | 'extract' | 'override' | 'grade'
  answer_key_id text,
  question_id   text,
  ai_category   text,                 -- AI 判的題型
  final_category text,                -- 最終（老師改後）題型
  signal_source text,                 -- 'header' | 'stem_wording' | 'answer_format'（分類依據）
  grading_path  text,                 -- 'code' | 'accessor' | 'vj' | 'rubric_judge' | 'table_group'
  vj_rubric_ok  boolean,              -- VJ 型是否成功生出 vjRubric
  meta          jsonb
);
create index on qtype_pipeline_log (stage, created_at);
create index on qtype_pipeline_log (ai_category);
```

**用途**：
- 分類分佈與訊號來源（classify）→ 監控線上題型分佈是否合理。
- 漂移事件（extract 的 final != skeleton 的 ai）→ 防漂告警。
- 老師 override（override）→ `ai_category → final_category` 是最直接的**分類品質訊號**（哪些型常被老師改＝AI 常判錯）。
- 批改路徑與 VJ 成功率（grade）→ 確認每型走對路徑、VJ 生得出 vjRubric。

寫入採 **fire-and-forget、不阻塞主流程、失敗不影響批改**（比照現有 usage log）。

## Phase 0 — 前置：測試集 ＋ baseline（不改 code）

- **做什麼**：收集 N 份真實題本（涵蓋 31 型代表題，含純題本／非純題本各若干），人工標 ground-truth 題型。
- **檢測方法**：對測試集跑**現有**分類，算 per-type 準確率當 baseline。
- **確認方式**：baseline 表建立、每型至少有代表樣本；缺樣本的型標記「待補題本」。
- **log**：baseline 結果可先寫 `qtype_pipeline_log(stage='classify', meta={eval:'baseline'})`。
- **harness**：`redpenaisever/scripts/qtype-baseline.mjs`（唯讀聚合 production 分佈，可重跑）。

### Phase 0 baseline 結果（2026-09-07，production answer_key_templates）

範本 99 份、總題數 **2263**。分佈（AI 現判，非 ground-truth）：
- **前 3 型佔 67%**：single_choice 29.4%、fill_blank 24.6%、word_problem 12.8%。
- 中量：true_false 3.8%、single_check 3.2%、short_answer 1.9%、circle_select_one 1.8%、calculation 1.7%、multi_check 1.3%。
- 其餘 <1%。
- **6 個零樣本型**（production 無例、測試集需另找題本）：`circle_select_many`、`mark_in_text`、`map_symbol`、`connect_dots`、`compound_writein_with_explain`、`compound_judge_with_correction`。
- ⭐ **`fill_variants` 僅 2（0.1%）**：注釋/造詞的目標型在真實資料極稀少——很可能大量注釋現正被判成 short_answer(42)/fill_blank(556)。**印證 Phase 1 分類修正的優先性**，也代表測試集要**刻意放注釋題**才驗得到。

**對測試集的意含**：① 按真實分佈加權（重壓 single_choice/fill_blank/word_problem）；② **刻意補**上述 6 零樣本型 + fill_variants/diagram_color/table_check 等稀有型；③ 注釋題要單獨備一組（驗證會不會正確落到 fill_variants）。
- **待辦**：抽樣做 ground-truth 標註算「現行準確率」（分佈≠準確率）；尤其抽 short_answer/fill_blank 看有無藏注釋。

### ⭐ Phase 1 驗證目標（數學卷抽出的 calc/word 界線）
- 數學 v2 把 **3-2/3-3/3-4 求面積題（8 cm²/477.28 m²/38.88 cm²）判成 word_problem**。按新規則「半情境（給邊長求面積）→ calculation」，這幾題**若無故事/人物應改判 calculation**——Phase 1 上線後要看這批有沒有正確翻成 calculation（這是新規則最直接的驗證點）。
- ⚠ **限制：answer_key JSONB 不存題幹**（只有 answer＋anchorHint 位置）。故 calc/word 的 ground-truth**無法從 DB 判**，須調實際題本圖（storage: `question_booklet_image_paths`）。→ Phase 1 驗證這條界線時要抓圖，不能只靠 DB。

### ⭐ 界線規則（此驗證集抽出，餵 Phase 1 分類 prompt）

1. **section 標題是最強訊號**：「注釋」→ fill_variants(注釋)；「國字注音」→ fill_variants(國字注音)；「是非」→ true_false；「選擇」→ single_choice。標題優先於答案格式。
2. **有 wordbank 的填空 ≠ fill_variants**：從固定字庫選填（水的現象凝固/凝結…、英語 wordbank）→ 答案唯一 → **fill_blank/multi_fill**，不可因為「有選項庫」誤判成 fill_variants(容多元)。
3. **填代號/配合/配對**：把代號填進( )或【】完成配對（成語填代號、國家公園配標籤）→ single_choice(配合) 或 matching。界定：**一對一連線/配對→matching；從共用代號庫填多格→single_choice(配合)**。待實測校準。
4. **circle 就地圈 vs ( )寫代號**：題幹「圈出」+選項就地→circle_select_one；「( )」寫代號→single_choice。靠題幹指示用詞區分（共用主判準生效）。
5. **聽力不影響題型**：英語聽力題的題型只看作答形式（圈/勾/寫/( )），與「是不是聽力」無關——回答了早先「AI 怎麼知道是聽力」的疑問：分類層不需要知道。
6. **compound 兩段要求**：「勾選+描述原因」「圈a/an+寫單字」→ compound_*（Bucket D），不可只判前半。

## Phase 1 — 步驟 1 落地：題本分析輸出 31 型（地基）

- **做什麼**：改 `buildSolveStructurePrompt` ＋ `SOLVE_TYPE_MENU`（`gemini.ts`）→ 輸出 db.ts 的 31 型，判準用「共用主判準（標題＞題幹用詞＞選項）＋非純加成」；退掉 7 型/6 型另兩套字彙、answer_only 也對齊。
- **檢測方法**：用 Phase 0 測試集回放，比對**新舊 per-type 準確率**＋**反向檢查**（原本判對、新版判錯的格數）。
- **確認方式**：整體準確率 ≥ baseline，且**無單一型大退化**；純題本子集另算一次。人工抽審 fill_variants/注釋、calc/word、圈選系列這些界線型。
- **log**：上線後每次題本分類寫 `stage='classify'`＋`ai_category`＋`signal_source` → 持續看線上分佈。
- **kill-switch**：env 保留舊 prompt 可切回。

## Phase 2 — 防漂不變量（單一來源保證）

- **做什麼**：確保 questionCategory 一次定於結構推斷、下游不重判；生成流程不落到 `AnswerBank.tsx:518` 的 25 型 fallback；`table_check` 正規化防漏。
- **檢測方法**：加不變量檢查——extract 後的 category 必等於 skeleton 的，不一致就記事件。
- **確認方式**：線上「extract category != skeleton category」事件數趨近 0；table_check 未正規化事件＝0。
- **log**：`stage='extract'`，不一致時 `meta={drift:true, skeleton_cat, extract_cat}`。

## Phase 3 — 題型可修正迴路（老師 override）

- **做什麼**：UI 開放老師改題型（31 型 optgroup 下拉），改動**連動換框＋標記需重批**。
- **檢測方法**：改題型後，作答框版型與批改路徑確實跟著換（幾個 case 手測）。
- **確認方式**：手測通過；且 override log 可用來回饋分類——「常被改的型」列出來回頭修 Phase 1 prompt。
- **log**：`stage='override'`＋`ai_category`＋`final_category`＋`question_id`。

## Phase 4 — 步驟 2 落地：bigbox＋底圖 ＋ 子類儲存

- **做什麼**：`AnswerSheetMakerStep` 加「這格放底圖/圖片」；生成器 box 支援 image；`fill_variants` 子類（注釋/造詞/國字注音）擷取時偵測並**存成欄位**（供選版型＋顯示）。
- **檢測方法**：生成幾份含各型的答案卷，檢查框正確、底圖可加、子類欄位正確。
- **確認方式**：視覺驗收；子類偵測抽樣正確率。
- **log**：可選——子類偵測結果進 `meta`。

## Phase 5 — 步驟 3 落地：VJ 擴充 ＋ visualAnswer 旗標 ＋ 補缺口

- **做什麼**：A0（`detectVisualRubric`）觸發範圍擴到畫圖類（connect_dots/diagram_draw）；加 `visualAnswer` 旗標（Phase 4 生 bigbox＋底圖時掛）→ 批改**只看旗標就走 VJ**、不看底層 category；補 `ordering` 的 Accessor bullet、`table_check` 正規化防漏。
- **檢測方法**：對這些型跑沙盒/回放批改；確認 VJ 生得出 vjRubric、判分合理（誤殺/放水檢查）。
- **確認方式**：各型批改準確率達標；`vj_rubric_ok` 成功率高。
- **log**：`stage='grade'`＋`grading_path`＋`vj_rubric_ok`。

## 依存與順序

```
Phase 0（測試集）
   └─ Phase 1（31型分類·地基）──┬─ Phase 2（防漂）
```
